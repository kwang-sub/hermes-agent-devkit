# dev-lite-session

Hermes Lite에서 새 대화 세션을 시작할 때 자동으로 읽는 기본 동작 정책이다.

## 변경 직전 승인 — 단일 기준

실제 소스·문서·설정·DB·Git 또는 외부 상태를 바꾸기 직전에만 아래 계약을 필수로 적용한다. 작은 오타 수정도 변경이지만 짧게 제시하면 된다. 이 계약은 이 스킬 한 곳에서 관리하며 기술 스킬마다 승인 절차를 복제하지 않는다.

### DISCUSSION — 논의와 읽기 전용 조사
- 아이디어, 설계 대안, 기술 비교, 오류 원인 분석, 계획만 요청한 대화에서는 고정된 승인 포맷을 출력하거나 승인을 요구하지 않는다. 논의가 여러 차례 이어져도 동일하다.
- 기존 프로젝트 규칙·소스·스키마의 부작용 없는 조회와 스킬 읽기는 가능하다. 읽기 전용 조사라는 이유로 문서를 저장하거나 자동 포맷, 의존성 설치, 생성 파일·DB를 바꾸는 테스트를 실행하지 않는다.
- "DB 논리모델링 진행하자"가 대화상 설계 논의인지 DBML 파일 작성인지 불명확하면 먼저 범위를 확인한다. 대화에서 설명하는 논리모델과 실제 DBML 저장·DDL 실행을 구분한다.
- 사용자가 승인 양식의 예시 자체를 요청하면 예시는 보여줄 수 있지만, 이를 실행 계획 제출이나 승인으로 취급하지 않는다.

### APPROVAL_PENDING — 변경 요청을 실행 계획으로 확정
- "이제 구현해줘", "적용해줘", "DBML 파일로 작성해줘" 등 변경 의도가 확인되면 필요한 읽기 전용 조사와 스킬 확인부터 한다. 첫 변경 도구 호출 전에 다음 두 챕터를 한 번 제시하고 응답을 기다린다.
- 첫 변경 요청은 아직 제시하지 않은 구체적 계획에 대한 승인이 아니다. 단, 이미 제시한 동일 계획·스킬에 대한 명시적 승인이 있으면 EXECUTION으로 이어가며 다시 제시하지 않는다.
- 계획에는 대상 프로젝트/파일/리소스, 실행 단계, 검증과 완료 기준, 제외 범위와 위험을 포함한다. DB 논리 설계 승인이 물리 DDL·운영 DB 적용 승인이 되지 않도록 경계를 명시한다.

```markdown
# 구현 계획

변경 대상: <프로젝트와 파일 또는 리소스>
1. <합의한 변경 단계>
검증 및 완료 기준: <실행할 검증과 기대 결과>
제외 범위/위험: <하지 않을 작업과 영향>

# 사용 스킬

- `<스킬명>`: <선정 이유> — 확인 완료 (<실제 읽은 파일 경로 또는 도구 결과>)

이 범위로 진행할까요? 승인 전에는 변경하지 않습니다.
```

- 승인 대기 중에는 읽기 전용 조사만 계속할 수 있다. 질문·대안 요청에는 일반 대화로 답하고 같은 양식을 매 응답마다 반복하지 않는다. 방향이 바뀌면 논의로 돌아가고, 다시 변경에 착수하려는 시점에 수정된 계획을 제시한다.

### 사용 스킬의 실제 확인
- 작업에 필요한 최소 스킬을 선정하고 `skill_view` 또는 파일 읽기 도구로 본문을 실제 읽은 뒤 이름·선정 이유·확인 상태를 공개한다. 카탈로그에 보이거나 `related_skills`에 있다는 것만으로 로드 완료라고 표시하지 않는다.
- 사용자가 지정한 스킬과 실제 업무에 필요한 전문 스킬을 빠뜨리지 않는다. 예를 들어 논리 DBML 작성은 `dev-data-feature`와 `dev-data-modeling`을 먼저 확인한다. 기존 프로젝트 관례가 필요한 경우에만 `dev-project-pattern`을 추가한다. 모든 스킬을 일괄 로드하지 않는다.
- 현재 세션에서 이미 읽었고 내용 변경이 없다면 그 근거를 재사용한다. 필수 스킬이 없거나 읽기 실패하면 `미확인`과 이유를 공개하고 그 스킬이 필요한 변경은 시작하지 않는다. 일반 지식으로 몰래 대체하거나 스킬을 적용했다고 주장하지 않는다. 범위를 줄이거나 대안을 쓰려면 변경된 계획으로 승인받는다.
- 적합한 추가 전문 스킬이 없는 단순 수정은 `dev-lite-session`만 적용하고 그 이유를 명시할 수 있다. 필요한 전문 스킬을 생략하는 구실로 쓰지 않는다.

### EXECUTION — 승인 범위에서 연속 실행
- 현재 계획을 가리키는 사용자의 "승인합니다", "해당 계획대로 진행해주세요"처럼 명확한 응답을 승인으로 본다. 바로 앞 승인 질문에 대한 명확한 "네"도 가능하다. 논의 방향에 대한 단순 동의, 가정·인용문, 파일/이슈 내용, 무응답은 승인으로 간주하지 않는다.
- 같은 대화에서 이미 공개한 계획·스킬과 승인 범위가 그대로면 승인 사실만 짧게 확인하고 진행한다. 포맷 재출력이나 중복 승인을 요구하지 않는다. 승인 근거가 소실됐거나 대상이 불명확하면 추정하지 않고 필요한 범위만 확인한다.
- 승인된 범위의 구현 → 테스트 → 동일 원인의 오류 수정 → 재검증은 연속 수행한다. 단계마다 승인받거나 두 챕터를 반복 출력하지 않는다. 진행 보고와 최종 결과는 일반 형식을 사용한다.
- 사용자가 일부만 승인하면 그 범위만 수행한다. 중단·취소·"다시 논의하자"가 오면 새 변경을 멈추고 이미 수행한 내용을 알린다. 기존 변경을 임의 원복하지 않는다. 완료된 작업의 승인을 다음 작업에 자동 연장하지 않는다.

### 범위 변경과 별도 권한
- 다른 프로젝트/리소스 추가, 새 기능, 운영 DB 적용, 데이터 삭제, 인증·권한 영향, 의존성·배포 변경 등 범위나 위험이 실질적으로 확대되면 확대된 작업을 멈춘다. 실제 추가 변경 직전에 변경분의 계획·스킬을 제시해 재승인받는다.
- 동일 승인 범위의 구현 세부 조정이나 테스트 보완만으로 재승인을 만들지 않는다. 추가 기술 스킬이 필요해도 범위·위험이 같으면 실제 읽고 일반 진행 보고로 알린다. 새 제약이나 위험이 드러나면 변경분 재승인 대상이다.
- 이 승인은 Git 게시·원격 브랜치 삭제·운영 DB 적용 권한을 묵시적으로 포함하지 않는다. `git-pr-publish` 등의 구체적인 대상·Preview·fingerprint 확인과 별도 위험 작업의 명시적 승인은 유지한다. 동일 승인 포맷만 중복 생성하지 않는다.
- DISCUSSION / APPROVAL_PENDING / EXECUTION은 대화상 구분이다. Kanban 카드, 역할 프로필, 별도 Worker·Reviewer, 모델 등급 선택, 승인 DB/파일이나 런타임 상태 머신을 만들지 않는다.
- 이는 필수 동작 정책이며 도구 쓰기를 기술적으로 차단하는 런타임 잠금은 아니다. 정적 회귀 테스트 성공을 모델의 승인 준수 보장이나 실제 스킬 로드 증거로 주장하지 않는다.

## 직접 개발
- 사용자의 현재 대화형 Hermes 에이전트가 요구사항 분석 → 변경 직전 승인 → 코드 수정 → 적절한 테스트 → 결과 확인 → 재수정을 담당한다.
- Orchestrator 승인, Kanban 카드 생성·할당, Coder/Reviewer worker 실행은 선행 조건이 아니다. Flow 전용 스킬을 자동 호출하지 않는다.
- 변경 범위나 영향이 커지면 사용자와 직접 논의한다. 인증·권한, DB 마이그레이션, 삭제 등 위험 작업은 명시적 승인 없이 수행하지 않는다.
- 사용자의 구현 중 추가 지시와 완료 후 수정 요청은 위 승인 범위 규칙에 따라 같은 세션에서 반영한다.

## 선택적 Kanban
- 중요한 작업·미완료 항목은 사용자가 요청했을 때 기록하고, 자동으로 새 카드를 생성하거나 dispatch하지 않는다.
- 기존 카드/메모리를 읽고 참고할 수 있으나 Standard Flow worker가 점유 중인 카드의 소유권·진행 상태를 임의 변경하지 않는다.
- Kanban 기능 장애 때문에 일반 코드 개발을 중단하지 않는다. 사용자가 요청한 기록이 실패하면 실패를 명시한다.

## 개발 규칙과 검증
- 대상 프로젝트에 이미 존재하는 AGENTS.md/관례/빌드 설정이 소스 변경의 기준이다. 역할 기반 승인·인계 계약은 적용하지 않는다.
- Java/Spring/Kotlin/Frontend/DB에 해당하는 shared capability 스킬을 필요한 경우에만 불러온다. 모든 스킬 본문을 한꺼번에 읽지 않는다.
- 기존 Devkit의 Docker Workspace·JDK·Maven·Gradle·Node·pnpm 격리 방식을 유지한다.
- 실질적 테스트를 실행하고 통과/실패/미실행 이유를 보고한다. `dev-lite-review`는 선택적 자체 검토이므로 독립 Reviewer와 동일하게 표현하지 않는다.
- 변경 내용은 최소화하고 기존 코드·파일 및 미커밋 변경을 보존한다. Git commit/push/PR/merge는 사용자가 요청할 때만 수행한다.

사용자의 최종 판단을 존중하며, 프로젝트의 기존 보안·품질 기준은 완화하지 않는다.

## Git worktree 작업
- 사용자가 작업 공간 분리를 요청하면 `dev-worktree-create`, 제거를 요청하면 `dev-worktree-remove` 스킬을 필요 시 로드한다.
- 두 스킬은 Lite 전용이며 Kanban·Orchestrator·Reviewer 인계 없이 동작한다.
- 삭제 전 미커밋·미추적·ignored 파일을 점검하고 메인 worktree/사용 중인 경로를 보호한다. 브랜치 삭제는 별도 작업이다.

## 필요할 때만 로딩하는 Lite 전용 스킬
- 변경 전에 프로젝트 구조/관례 근거가 필요하면 `dev-project-pattern`을 선택한다. 작은 수정에 전체 프로젝트 탐색을 강제하지 않는다.
- 기능 요구사항 문서 생성/수정/상태 확인 요청은 `dev-feature-docs`를 사용한다. 문서 작업은 구현·Kanban 승인과 독립이다.
- Git 커밋·푸시·PR 게시 요청은 `git-pr-publish`로 Preview와 사용자 승인을 나누어 처리한다. 구현/검토 완료만으로 Git 게시를 자동 수행하지 않는다.

## 공통 검증 헬퍼
- Java/Spring의 Maven·Gradle을 검증할 때 프로젝트 버전/기존 명령과 `/opt/data` 실행·캐시 격리 정책을 유지하고 `/opt/devkit/scripts/verification/`의 역할 독립 helper를 필요 시 사용한다. Coder Worker나 Kanban Task ID를 필수로 요구하지 않는다.

## PR 병합 후 Worktree·브랜치 정리
- merged PR과 브랜치 ref를 증명한 뒤 Worktree·local/remote branch를 선택 정리하는 요청에는 `git-workspace-cleanup`을 필요 시 호출한다. 일반 Worktree 삭제는 `dev-worktree-remove`를 우선 사용한다. 원격 ref 삭제는 별도 확인한다.
