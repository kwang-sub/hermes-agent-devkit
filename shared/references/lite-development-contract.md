# 직접 개발의 책임과 안전 경계

현재 default 세션이 분석·설계·구현·검증을 담당한다. 단계 분리는 산출물과 위험 경계를 명확히 하기 위한 것이며 별도 Kanban 카드, 프로필, Worker, 승인 UI를 생성하는 계약이 아니다.

변경 직전 승인 포맷과 스킬 확인은 `dev-lite-session`의 단일 계약을 따른다. 논의 중에는 승인 양식을 출력하지 않고 실제 변경 착수 직전에만 한 번 확인한다. 기술 capability마다 같은 승인 절차를 추가하지 않으며, 승인된 구현·테스트·동일 범위의 재수정은 연속 수행한다.

복잡한 작업은 목표·이번 범위·제외 범위·기존 근거·예상 변경·최소 검증·위험을 짧게 정리한다. 작은 수정에는 전체 설계 문서를 요구하지 않는다. 단계별 기술 계획은 `dev-project-pattern`을 활용한다.

논리 모델의 의미를 먼저 확정한 후 물리화/마이그레이션을 별도 승인 단계로 다룬다. 같은 대화에서 이어갈 수 있으나 설계 요청만으로 DDL 실행을 승인받았다고 판단하지 않는다. migration 파일 작성과 실제 DB 적용도 별도 권한이다. API breaking change, 인프라/의존성 변경, 인증/인가, 데이터 삭제는 영향과 복구 방법을 설명하고 명시적 승인을 확인한다.

기능 문서와 설계 문서는 구현 근거를 기록할 뿐 작업 실행 엔진이 아니다. 현재 코드·실제 테스트 근거를 벗어나 완료를 선언하지 않는다. 검증 수준·캐시 재사용은 `verification-level-policy.md`를 따른다.
