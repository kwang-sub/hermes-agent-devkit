# 백엔드 테스트 작성 스타일

Canonical policy: `BACKEND_TEST_STYLE_POLICY_V1`.

백엔드 테스트를 작성하거나 수정할 때만 읽는다. 비즈니스 규칙은 시나리오형, 일반 기술 기능·입출력 계약은 단일 Given–When–Then 형태를 기본으로 한다. BehaviorSpec도 Given–When–Then을 사용하는 표현 방식이므로 서로 다른 검증 방법으로 취급하지 않는다.

## 적용 순서와 기존 코드 보존

현재 작업의 명시적 사용자 지시를 먼저 확인한다. 기존 테스트 파일에 케이스를 추가하거나 수정할 때는 기존 스타일을 유지한다. 스타일을 맞추려고 파일을 다시 쓰거나, 같은 파일에 다른 Spec 구조를 섞거나, 관계없는 테스트를 일괄 전환하지 않는다.

새 테스트 클래스는 프로젝트의 언어·설치된 테스트 도구·지원 버전과 명시적 테스트 규격을 확인한 뒤 아래 기본값을 적용한다. 기존 규격이 특정 스타일을 요구하면 그 규격을 유지한다. 새 파일을 만들어 기존 스타일 보존 원칙을 우회하지 않는다. 패키지·파일명·fixture·assertion 관례도 유지한다.

테스트 도구나 지원 여부를 확인하지 못했으면 BehaviorSpec 등을 사용할 수 있다고 보고하지 않는다. 확인된 기존 방식으로 가능한 범위만 진행하고, 필요한 도구가 없으면 해당 테스트를 미실행으로 구분한다. 스타일 때문에 Kotlin·Kotest·JUnit이나 새 의존성을 자동 추가·교체·업그레이드하지 않는다.

## 검증 대상에 따른 선택

클래스 이름이나 계층이 아니라 **테스트가 확인하려는 규칙과 기대 결과**로 분류한다. Service라고 모두 비즈니스 테스트가 되는 것은 아니며, Controller·Repository라도 업무 규칙을 검증할 수 있다.

- 비즈니스 규칙: 업무 조건에 따른 허용·거절, 상태 전환, 계산 규칙, 사용자 시나리오의 결과를 확인한다.
- 일반 기술 기능·입출력 계약: 변환, 직렬화, 매핑, 프로토콜 형식, 데이터 접근 동작 등 기술적 결과를 확인한다.
- 한 작업에 둘 다 있으면 검증 책임별로 나누어 선택한다. 파일 하나나 기능 전체를 억지로 한 분류에 넣지 않는다. 분류가 모호하고 구조를 나누는 이점이 없으면 기존 스타일 또는 단순한 Given–When–Then을 유지한다.

| 대상 | 확인된 테스트 환경 | 기본 작성 스타일 |
|---|---|---|
| 비즈니스 규칙·사용자 시나리오 | Kotlin + Kotest에서 지원 확인 | BehaviorSpec |
| 비즈니스 규칙·사용자 시나리오 | Java·Kotlin + JUnit Jupiter | JUnit @Nested + Given–When–Then |
| 일반 기술 기능·입출력 계약 | Kotlin + Kotest에서 지원 확인 | FunSpec 등 기존 단순 Spec + Given–When–Then |
| 일반 기술 기능·입출력 계약 | Java·Kotlin + JUnit Jupiter | 일반 @Test + Given–When–Then |
| 어느 대상이든 | JUnit 4·기타 엔진 또는 명시적 프로젝트 규격 | 지원하는 기존 스타일에서 조건·행위·기대 결과 표현 |

JUnit의 시나리오형을 BehaviorSpec이라고 부르지 않는다. 중첩은 조건별 차이를 이해하는 데 도움이 될 때만 사용하며, 한 시나리오를 위해 의미 없는 @Nested 계층을 만들지 않는다. 기존 BehaviorSpec 파일에 기술 검증을 보완하는 경우에도 파일의 스타일을 유지한다.

## 작성 품질과 실행 범위

준비 조건·검증할 행위·기대 결과가 읽히도록 작성한다. 예외 검증처럼 실행과 확인이 함께 표현되는 경우 when & then을 허용하며 세 구간을 억지로 분리하지 않는다. 하나의 테스트는 하나의 시나리오나 규칙을 다루되 관련된 여러 assertion은 허용한다.

상위 블록의 변경 가능한 객체·Mock·DB 데이터를 하위 테스트가 공유하여 실행 순서에 의존하지 않게 한다. 각 테스트를 단독 실행할 수 있도록 데이터와 호출 기록을 테스트 생명주기에 맞춰 독립적으로 준비한다. 이를 위해 실행 엔진의 격리 모드를 임의로 변경하지 않는다.

작성 스타일과 단위·통합 테스트 선택은 별개다. 시나리오형이라는 이유로 @SpringBootTest를 강제하지 않으며, 실제 DB 쿼리·매핑 동작을 Mock만으로 검증했다고 보고하지 않는다. 실행 범위·명령·격리는 기존 `verification-level-policy.md`와 관련 기술 스킬을 따른다.

Java·Kotlin의 한글 표시명은 기존 `jvm-test-display-name-policy.md`를 그대로 적용한다. Kotest에는 DSL의 한글 설명을 사용하고 JUnit annotation을 억지로 붙이지 않는다. 스타일 선택이 한글 표시명이나 실제 동작 검증을 대신하지 않는다.

## 사용자에게 알리는 범위

백엔드 테스트 작성·수정이 포함된 작업에서는 기존 구현 계획의 검증 항목에 **테스트 스타일을 한 줄로 한 번만 안내**한다. 실제 도구와 선택한 형태만 적고 내부 분류 과정, 장황한 선택 이유, 코드 예시나 샘플을 출력하지 않는다. 여러 스타일이 필요하면 같은 줄에 대상별로 구분하고, 기존 파일을 유지하면 기존 스타일 유지라고 알린다.

테스트 스타일 전용 선택창·추가 승인·새 챕터를 만들지 않는다. 동일 작업의 테스트 실행·재시도마다 반복하지 않는다. 스타일이 바뀌면 변경 사실만 짧게 알리고, 의존성이나 작업 범위가 확대되는 경우에만 기존 `dev-session` 승인 정책을 따른다. 테스트를 작성·수정하지 않는 단순 실행이나 무관한 작업에는 이 안내를 강제하지 않는다.

이 한 줄은 스타일 선택 안내만 줄이는 것이다. 기존 구현 계획·사용 스킬 안내·승인 절차를 생략하지 않는다. 최종 보고에서도 실제 실행 명령과 통과·실패·미실행 사유·잔여 위험을 계속 구분한다.

## 정책만 유지

이 정책을 위해 샘플 코드·샘플 테스트 프로젝트·복사용 템플릿·공통 테스트 부모 클래스를 추가하지 않는다. 기존 참고 샘플은 삭제하거나 스타일 통일 대상으로 삼지 않는다. 실제 개발 작업에서는 대상 프로젝트와 가까운 기존 테스트를 읽고 필요한 테스트 코드를 작성한다.

DevKit 자체 회귀 검사는 정책 문구와 스킬 연결 누락을 확인하는 정적 검사다. 실제 모델의 스타일 선택·생성 품질·안내 준수, JUnit·Kotest 실행이나 대상 프로젝트 테스트 성공을 보장하지 않는다. 별도 스타일 판정 프로그램이나 런타임 차단 장치는 추가하지 않는다.
