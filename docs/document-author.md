# 문서 작성 스킬 사용 방법

`dev-document-author`는 문서의 내용·문체·검토 기준을 담당한다. 실제 DOCX/PPTX/XLSX/CSV 작업은 `microsoft-office`, PDF 작업은 `pdf`를 사용한다. 설치된 스킬과 실행 도구를 확인한 뒤 해당 기능만 사용하며, `humanizer`는 선택 사항이다.

## 가장 중요한 기준

독자가 실제 업무에서 사용하는 말로 자연스럽게 쓴다. 불필요한 수식어·번역투·추상적인 칭찬을 줄이되 수치·조건·부정·예외·전문 용어는 보존한다. 이미 자연스러운 문장은 그대로 둔다. `최적화` 같은 단어를 무조건 금지하거나 단어 수로 평가하지 않는다.

예: `처리 상태에 대한 확인을 수행할 수 있습니다.` → `처리 상태를 확인할 수 있습니다.`

`할 수 있습니다`를 `해야 합니다`로 바꾸는 것은 문체 수정이 아니라 의미 변경이므로 허용하지 않는다.

## 요청 예시

```text
dev-document-author 스킬로 아래 초안을 고객사 안내문으로 다듬어 주세요.
합니다체를 유지하고, 수치와 처리 조건은 바꾸지 마세요.
```

```text
제공한 API 명세를 바탕으로 연동 가이드를 DOCX와 PDF로 작성해 주세요.
API 경로와 필드명은 그대로 두고, 고객사 개발자가 읽기 쉽게 설명해 주세요.
PDF는 DOCX의 레이아웃을 유지하는 변환본이 필요합니다.
```

```text
이 PPTX의 제목과 설명만 자연스럽게 고쳐 주세요. 수치와 슬라이드 순서는 유지해 주세요.
```

```text
이 XLSX의 표 제목과 설명문만 다듬어 주세요. 수식과 데이터 값은 수정하지 마세요.
```

문서 파일을 만들지 않고 대화 안에서 문장만 다듬을 수도 있다. 파일 생성·변환은 실제 설치된 공식 스킬과 도구가 있을 때만 가능하다. 변환기가 없으면 PDF를 임의로 다시 만든 뒤 변환에 성공했다고 보고하지 않는다.

## DevKit 연결

새 스킬은 `custom-skills/shared/dev-document-author/`에 있다. 기존 shared 경로를 사용하므로 별도 서비스나 새로운 마운트를 추가하지 않는다. 기본 자동 로드는 기존 `dev-session`만 유지한다. 새 정책과 포맷 참조는 문서 작업 때 필요한 것만 읽는다.

변경 전 승인은 기존 DevKit 절차를 따른다. 기능 문서는 `dev-feature-docs`, API 계약은 `dev-api-docs`의 책임을 유지한다. 공식 스킬·사용자 원본·컨테이너 설정을 자동으로 초기화하거나 바꾸지 않는다. 업데이트를 반영한 뒤 새 Hermes 세션에서 스킬 본문이 실제로 읽히는지 확인한다.

## 자동 검증

저장소 루트에서 실행한다.

```bash
python3 custom-skills/shared/dev-document-author/tests/test_document_policy.py
bash scripts/verify.sh
```

기존 회귀 실행기가 신규 테스트를 자동으로 찾는다. 정책과 참조 파일, 예문의 보호 값, 스킬 등록, 기본 자동 로드 유지 여부를 검사한다. 이 테스트는 실제 LLM 문장 생성이나 DOCX/PDF 렌더링 테스트가 아니다. 별도 외부 모델 호출이나 문서 생성 의존성을 CI에 추가하지 않는다.

## 실제 환경에서 확인할 항목

| 요청 | 확인할 결과 |
|---|---|
| 한국어 가이드 DOCX/PDF | 내용 일치, 한글 글꼴, 표 잘림, 변환 여부 |
| 기존 문서 부분 수정 | 범위 밖 내용과 자연스러운 기존 표현 보존 |
| PPTX 제목·노트 수정 | 수치·슬라이드 구성 유지, 텍스트 겹침 여부 |
| XLSX 제목·설명 수정 | 수식·셀 값·시트 보존, 필요한 계산 검증 |
| 공식 스킬·변환기 없음 | 해당 출력만 미완료, 임의 설치나 성공 보고 없음 |

가상 자료로 확인하고 실행 환경, 읽은 스킬, 명령·결과, 미검증 항목을 기록한다. 자동 테스트 통과만으로 위 항목을 통과했다고 표시하지 않는다. Windows updater의 모의 검증 역시 사용자 PC에서 실제 업데이트한 결과와 구분한다.
