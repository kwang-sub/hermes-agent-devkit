# Screen Specification Behavior Contract

`screen-spec.md`는 화면 기능, UI 표현, 사용자 조작, 결과, 검증 기준을 연결한다.
이미지는 보이는 구조의 근거이며 보이지 않는 제품 동작을 자동으로 승인하지 않는다.
이 문서가 동작 명세의 canonical 작성 규칙이다. Feature/Test Skill은 이 규칙을 참조한다.

## 적용 범위와 호환성

- 기존 경로 `docs/ui/screens/<screen>/screen-spec.md`와 이미지 이름/viewport 규약은 유지한다.
- 신규 명세와 기능/UI/상태 흐름을 의미 있게 변경하는 명세는 `spec_version: 2`로 작성한다.
- 오탈자·경로 설명만 수정하거나 기존 문서를 읽는 경우 일괄 마이그레이션하지 않는다.
- 버전 없는 명세와 `spec_version: 1`은 기본 guard에서 읽을 수 있다. 결과는
  `BEHAVIOR_CONTRACT_STATUS=LEGACY_NOT_CHECKED`이며 동작 명세가 검증됐다는 뜻이 아니다.
- `spec_version: 2`는 아래 네 섹션과 연결표를 검사한다. 새 문서의 버전을 생략하여 검사를 우회하지 않는다.
- 이미지뿐 아니라 FIGMA 기반 Screen Spec에도 동일한 동작 규칙을 적용한다.
- CODE_DRIVEN 작업에 기존 Screen Spec이 있으면 같은 동작 규칙을 소비한다.
  없는 경우 기존 프로젝트 문서 관례를 유지한다. 검사를 위해 가짜 IMAGE/Figma reference를 만들지 않는다.
- 이 guard는 기존 reference 메타데이터에 IMAGE/FIGMA만 허용한다. EXISTING_CODE 메타데이터를
  새로 도입하거나 기존 API/source 정책을 바꾸는 작업은 이번 계약 범위가 아니다.

## 승인과 근거

`status: DRAFT | REFERENCE | APPROVED`는 디자인 상태다.
`behavior_status: DRAFT | APPROVED`는 기능 동작의 별도 승인 상태다. v2에서 필수다.
동작 명세의 초깃값은 `DRAFT`다. 이미지 승인이나 guard 통과로 동작을 자동 승인하지 않는다.

기능별 `확정 상태`는 `CONFIRMED | PROPOSED | UNKNOWN`이다.
`근거`에는 사용자 요구/승인 기록, 요구사항 문서의 항목, 기존 구현의 경로와 확인 내용을 적는다.
기존 코드에서 관찰한 사실과 새 동작 제안을 구분한다. 코드가 존재한다는 사실이
새 동작 변경을 승인했다는 뜻은 아니다. 상세 동작에는 UNKNOWN이 남을 수 있으며
`UNKNOWN: 원인과 필요한 결정`처럼 명시한다. 미확정 항목을 빈칸이나 임의의 동작으로 대체하지 않는다.

`behavior_status: APPROVED`인 명세의 범위 내 기능은 모두 `CONFIRMED`여야 한다.
새 제품 동작의 승인 이력과 사실상 중요한 미확정 사항의 해소 여부는 Reviewer가 확인한다.
guard는 기록된 상태와 구조만 검사하며 실제 승인자를 검증하지 않는다.
이미 승인된 화면의 의미 있는 동작을 바꾸면 기존 디자인 승인은 유지할 수 있지만
동작 상태는 `DRAFT`로 되돌리고 변경된 기능/근거를 갱신한다. 검토되지 않은 새 동작을
기존 `APPROVED` 표시에 편승시키지 않는다.

## 필수 섹션

### 화면 기능 목록

정확한 제목은 `## 화면 기능 목록`이다.
컬럼은 `기능 ID | 기능명 | 사용자 목적 / 설명 | 연결 UI ID | 확정 상태 | 근거`다.

F-01 형식의 안정적인 ID로 기능을 식별한다. 버튼 개수가 아니라 사용자가 할 수 있는 일로 나눈다.
자동 조회, 카드·표·차트의 정보 제공, 안내문 확인도 기능이 될 수 있다.
실제 이번 화면에 제공할 기능을 기록한다. 향후 기능/이번 범위 밖 요소는 범위 외로 별도 표시하며
미승인 기능을 구현 범위에 섞지 않는다. 삭제된 ID를 다른 의미로 재사용하지 않는다.

### UI 요소 및 기능 연결

정확한 제목은 `## UI 요소 및 기능 연결`이다.
컬럼은 `UI ID | 요소 / 종류 / 표시명 | 위치 / 영역 | 연결 기능 ID | 노출 조건 | 활성화 / 표시 규칙 | 플랫폼 차이`다.

UI-01 형식의 ID를 사용한다. 실제 라벨/아이콘의 접근 가능한 이름, 위치, 연결 기능을 적는다.
노출/숨김과 활성/비활성을 구분한다. 정보 표시 요소는 값의 의미·형식·단위·빈값 규칙을 적는다.
표는 컬럼과 정렬/페이지 이동, 차트는 축/범례/설명 제공 등 실제 제공하는 동작만 설명한다.
모든 HTML 노드나 단순 장식을 나열하지 않는다. 화면에 보이는 의미 있는 요소가 기능에 연결되지
않으면 누락/범위 외/장식 중 무엇인지 검토한다. 이미지에 보이지 않는 조건부 UI도 명세에 포함한다.

한 기능에 여러 UI, 한 UI에 여러 기능을 연결할 수 있다. 두 표의 관계는 양방향으로 같아야 한다.
여러 ID는 쉼표로 구분한다. 관련 UI가 없는 자동 동작만 `연결 UI ID: NONE`과 상세의
`관련 UI: NONE`을 허용한다. 그때 `미노출 사유`를 반드시 적는다.
화면 전체에 의미 있는 UI가 전혀 없으면 UI 섹션의 본문을 `NONE` 한 줄로 적을 수 있다.
자동 실행이라도 화면에 결과를 보여준다면 그 결과 UI와 연결한다.

웹/모바일은 기능 ID를 공유하고 제공 방식의 차이만 적는다. 예: 웹 팝오버, 모바일 바텀시트.
플랫폼 한쪽을 기능 범위에서 제외하려면 요구사항 근거와 대체 경로/제약을 명시한다.

### 기능별 동작 명세

정확한 제목은 `## 기능별 동작 명세`다. 각 기능은 `### F-01 — 기능명` 형태로 작성한다.
각 기능 아래에 `항목 | 동작 명세` 2열 표를 둔다. 최소 행은 다음과 같다.

| 항목 | 기록할 내용 |
| --- | --- |
| 관련 UI | 기능 목록과 동일한 UI ID 집합 |
| 실행 시점 | 클릭/Enter/입력 변경/화면 진입 등과 자동 실행 여부 |
| 사전 조건 / 입력 검증 | 권한, 기본값, 입력 제약과 잘못된 입력의 표시 위치 |
| 정상 결과 | 갱신되는 값/영역과 관찰 가능한 결과 |
| 상태 / 예외 처리 | 필요한 처리 중/빈 결과/실패 상태와 사용자 피드백 |
| 화면 이동 / 저장 | 이동 대상, 상태 유지/초기화, 저장 여부 및 하지 않는 동작 |
| 플랫폼 차이 | 웹/모바일 공통·차이, 키보드/터치 대체 조작 |

위 필수 행이 해당하지 않으면 `해당 없음: 정적 안내이므로 입력을 받지 않는다`처럼 이유를 적는다.
단독 `NONE`, `N/A`, `TODO`, `TBD`, 빈칸, 템플릿 자리표시는 완료된 설명이 아니다.

실제 필요한 경우 로딩 처리/빈 결과/실패/재시도·중복 방지/포커스·닫기·취소 행을 추가한다.
조회 기능은 재조회 중 기존 결과 처리, 입력과 표시 결과의 기간 일치, 중복 요청 여부를 명시한다.
저장/삭제 기능은 확인·취소, 성공/실패 시 입력 보존과 중복 실행 방지를 명시한다.
설명 패널은 열기/닫기, 기본 표시, 키보드 접근과 포커스 복귀를 명시한다.
모든 기능에 모든 상태를 기계적으로 요구하지 않는다. 공통 정책은 문서 경로/항목을 참조한다.
API/DB 세부 계약은 별도 명세를 참조하고 Screen Spec에 DTO/DB 규칙을 중복 정의하지 않는다.

### 기능별 검증 조건

정확한 제목은 `## 기능별 검증 조건`이다.
컬럼은 `검증 ID | 기능 ID | 사전 조건 / 상태 | 사용자 조작 / 트리거 | 기대 결과 | 검증 방법`이다.

AC-01 형식의 ID를 사용한다. 모든 기능에는 최소 한 개의 관찰 가능한 검증 조건을 연결한다.
복잡한 기능은 노출/권한, 입력 제약, 성공, 빈 결과, 실패·재시도, 플랫폼 차이 중 해당 사례를 추가한다.
표의 검증 방법은 계획이며 PASS 증거가 아니다. Coder/Reviewer handoff에서
`AC-ID → F-ID → UI-ID → 실제 테스트/수동 증거 → PASS | FAIL | NOT_RUN`을 남긴다.
기능 테스트와 이미지 일치/시각 회귀 검증을 별도로 보고한다.

## 작성과 구현 순서

화면 목적/범위 → 기능 목록 → UI 연결 → 동작/미확정 항목 → 검증 조건 → 승인 근거 → 구현 순서로 확인한다.
사용자/Task의 명시 요구를 우선하며, 이미지에서 관찰한 사실과 동작 명세가 충돌하면
추측으로 해결하거나 모든 문서 중 하나를 무조건 우선하지 않고 차이를 기록한다.
확정된 기존 규칙을 다시 승인받지 않는다. 실제 제품 결정을 요구하는 미확정 기능만 승인 대상으로 분리한다.

기존 `주요 영역`, `관찰된 디자인`, `상태`, `View Strategy`, `구현 구조`, `반응형`,
`Interaction / Navigation`, component/token, API/dependency, Unknown, Acceptance Criteria는 유지한다.
기능 동작의 중복 정의 대신 F/UI/AC-ID를 참조한다. ID는 문서용이며 DOM id/test-id 생성 의무가 아니다.

## 검사 호출과 결과

기존 문서 읽기:

```bash
python3 /opt/custom-skills/shared/dev-design-reference/scripts/screen_spec_guard.py --spec docs/ui/screens/<screen>/screen-spec.md
```

신규/의미 있게 수정한 문서 구조 확인:

```bash
python3 /opt/custom-skills/shared/dev-design-reference/scripts/screen_spec_guard.py --spec docs/ui/screens/<screen>/screen-spec.md --require-behavior-contract
```

그 문서의 승인된 동작을 구현하는 단계:

```bash
python3 /opt/custom-skills/shared/dev-design-reference/scripts/screen_spec_guard.py --spec docs/ui/screens/<screen>/screen-spec.md --require-approved-behavior
```

`--require-approved-behavior`는 v2 요구를 포함한다. 기획 중 DRAFT 문서는 구조 검사만 한다.
디자인 `status` 및 기존 환경/승인 Gate는 별개이며 이 옵션으로 우회하지 않는다.
기존 승인 범위의 작은 구현 수정에서 명세를 새로 승인받는 절차를 추가하지 않는다.

`BEHAVIOR_CONTRACT_STATUS=STRUCTURE_PASS`는 필수 섹션/셀, ID 중복, 존재하지 않는 참조,
기능↔UI 양방향 연결, 상세 동작/AC 누락이 없다는 뜻이다. 기능 정확성/디자인 일치/실제 승인/테스트
성공을 보증하지 않는다. 본문 설명이 실제 UI를 빠짐없이 나타내는지는 Reviewer와 기능 테스트가 확인한다.

지원 문법은 지정된 제목과 단일 행 Markdown pipe table이다. literal pipe는 `\|`로 이스케이프한다.
inline code ID와 표 셀의 `<br>`는 허용하지만 multiline cell, 복잡한 HTML 표, 임의의 제목 별칭은 지원하지 않는다.
코드 펜스와 HTML 주석 안의 예시는 검증 대상에서 제외한다. 일반 Markdown/YAML parser를 가장하지 않는다.
