# 로그·코드 분석 보고

아래 다섯 항목으로 결과를 보고한다. 기본은 항목당 1~3개 요점으로 짧게 쓰고, 복잡한 문제나 상세 설명 요청에만 늘린다. 사용자가 지정한 양식·길이·언어를 우선한다. 자연스러운 한국어로 결론부터 쓰며 같은 내용을 반복하지 않는다.

## 분석 원칙

1. 제공된 로그·코드·설정에서 대상과 버전을 확인한다. 빠진 정보는 추측해 채우지 않는다. 먼저 확인 가능한 범위를 분석하고, 결론을 바꿀 핵심 정보만 추가로 요청한다.
2. 오류는 발생 지점과 앞뒤 로그, 예외 연결, 관련 호출부를 함께 확인한다. 오류 메시지가 가리키는 증상과 근본 원인을 구분한다. 코드 설명은 입력 → 분기·호출 → 반환값·부수 효과 순으로 읽는다. 실행하지 않은 코드는 정적 분석이며 예상 결과라고 표시한다.
3. 주요 판단을 **확인 / 추정 / 미확인**으로 구분한다. `확인`에는 직접 읽은 근거를 연결하고, `추정`에는 근거와 확인 방법을 적는다. 실행 결과·줄 번호·환경·원인 확률을 만들어 쓰지 않는다. 정상 동작에는 문제나 수정안을 억지로 만들지 않는다.
4. 기술의 일반 동작은 공식 문서로, 해당 사례의 원인은 실제 로그·코드·설정·재현 결과로 뒷받침한다. 문서에 유사한 설명이 있다는 이유만으로 실제 원인을 확정하지 않는다. 근거 없는 원인을 나열하지 말고 유력한 후보부터 설명한다.
5. 분석 요청에서는 읽기와 설명을 기본으로 한다. 제안한 조치와 실제 수행한 조치를 구분한다. 파일 수정·설정 변경·재시작 등은 현재 요청의 승인 범위와 `dev-session`을 따른다. 새 승인 절차나 실행 서비스를 만들지 않는다.

## 공식 문서 확인

- 외부 기술의 동작·설정·버전 차이를 판단할 때 `dev-official-docs-context`를 읽고 실제 버전에 맞는 공식 문서 조회 방법을 재사용한다. 이 보고에서는 문서의 버전 일치 여부를 짧게 설명하며 내부 상태값이나 인계 양식을 그대로 출력하지 않는다.
- 문서 본문을 직접 확인하고 해당 주장을 뒷받침하는 절의 URL을 제시한다. Context7 등을 통해 읽은 경우에도 원문 공식 URL과 지원하는 내용을 확인한다. 검색 결과의 제목·요약만으로 확인했다고 하지 않는다.
- 제조사·프로젝트 공식 문서, 표준 명세, 공식 저장소의 소스·릴리스 노트를 사용한다. 공식 소스·이슈를 참고했다면 자료 종류를 명시하고, 이슈의 주장만으로 동작이나 버그를 확정하지 않는다. 블로그·커뮤니티 글을 공식 근거로 표시하지 않는다.
- 대상 버전을 모르면 `대상 버전 미확인`, 다른 버전만 확인했으면 적용 한계를 적는다. 최신 문서를 현재 환경에 그대로 적용하지 않는다. 검색어에는 오류 종류·기술명 등 필요한 공개 정보만 넣고 비밀번호·토큰·개인정보·내부 주소·비공개 코드 전체를 보내지 않는다.
- 핵심 근거 1~3개를 우선하고 필요한 경우만 늘린다. 각 링크를 본문의 판단과 연결한다. 홈페이지 링크만 모으거나 URL·절 제목·인용문을 만들어 채우지 않는다.
- 문서 접근에 실패하거나 근거를 찾지 못하면 `공식 문서 미확인`과 이유를 적고 확인한 코드·로그 범위로 결론을 제한한다. 외부 기술의 동작을 근거로 삼지 않는 순수 업무 로직은 `프로젝트 내부 로직: 코드 근거 기준`으로 표시한다.

## 보고 형식

아래 제목과 순서를 유지하되 안내 문구는 실제 분석 내용으로 바꾼다. 내용이 없으면 해당 항목에 이유를 한 줄로 적는다.

### 1. 결론

핵심 원인 또는 코드의 동작·차이를 1~2문장으로 설명하고 확인 수준을 표시한다. 원인을 확정할 수 없으면 현재 확인한 범위부터 적는다.

### 2. 확인 근거

핵심 로그 구절, 파일·함수·확인한 줄 번호, 설정·입력값을 필요한 만큼만 제시한다. 민감정보는 가린다. 제공된 자료·직접 실행한 결과·정적 분석을 구분한다.

### 3. 원인 또는 동작

오류는 발생 조건과 실패 흐름을, 정상 코드는 실행 순서와 결과를 설명한다. 추정 원인에는 그 판단의 근거와 아직 모르는 점을 적는다. 공식 문서가 뒷받침하는 주장에는 문서 번호 또는 링크를 연결한다.

### 4. 조치와 확인 방법

필요한 최소 조치와 성공 여부를 판단할 검증 방법·기대 결과를 적는다. 정상 코드 설명은 예시 입력과 예상 결과로 대신할 수 있다. 추가 조치가 필요 없으면 그렇게 적는다. 미실행 명령·테스트는 `제안`, 수행한 것은 실제 결과로 표시한다.

### 5. 공식 문서

각 근거를 `번호. [문서명 — 해당 절](확인한 공식 URL) — 문서 버전과 뒷받침하는 판단`으로 적는다. 확인한 URL만 넣고, 미확인 또는 순수 업무 로직이면 위 규칙에 따른 사유를 적는다.

## 완료 확인

결론이 제시한 증거보다 강하지 않은지, 링크가 관련 주장과 버전을 뒷받침하는지, 제안과 수행 결과를 구분했는지 확인한다. 기본 결과물은 대화의 분석 보고다. 문서 파일을 요청받은 경우에만 `dev-document-author`와 해당 포맷의 공식 스킬로 출력한다.
