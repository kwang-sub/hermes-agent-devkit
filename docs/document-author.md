# 문서 작성 스킬 사용 방법

`dev-document-author`는 문서의 내용·문체·검토와 시안 선택 흐름을 담당한다. v0.2.0부터 신규·재디자인 PPT는 HTML 시안을 먼저 제시하고 선택 후 PPTX를 제작한다. 실제 파일 작업은 설치·검증된 `microsoft-office`, `pdf` 또는 지원 기능을 확인한 `tabella`를 사용한다. 설치된 스킬과 실행 도구를 확인한 뒤 해당 기능만 사용하며, `humanizer`는 선택 사항이다.

## 가장 중요한 기준

독자가 실제 업무에서 사용하는 말로 자연스럽게 쓴다. 불필요한 수식어·번역투·추상적인 칭찬을 줄이되 수치·조건·부정·예외·전문 용어는 보존한다. 이미 자연스러운 문장은 그대로 둔다. `최적화` 같은 단어를 무조건 금지하거나 단어 수로 평가하지 않는다.

예: `처리 상태에 대한 확인을 수행할 수 있습니다.` → `처리 상태를 확인할 수 있습니다.`

`할 수 있습니다`를 `해야 합니다`로 바꾸는 것은 문체 수정이 아니라 의미 변경이므로 허용하지 않는다.

## 요청 예시

```text
dev-document-author 스킬로 아래 초안을 고객사 안내문으로 다듬어 주세요.
합니다체를 유지하고, 수치와 처리 조건은 바꾸지 마세요.
```

```text
제공한 API 명세를 바탕으로 연동 가이드를 DOCX와 PDF로 작성해 주세요.
API 경로와 필드명은 그대로 두고, 고객사 개발자가 읽기 쉽게 설명해 주세요.
PDF는 DOCX의 레이아웃을 유지하는 변환본이 필요합니다.
```

```text
이 PPTX의 제목과 설명만 자연스럽게 고쳐 주세요. 수치와 슬라이드 순서는 유지해 주세요.
```

```text
이 XLSX의 표 제목과 설명문만 다듬어 주세요. 수식과 데이터 값은 수정하지 마세요.
```

문서 파일을 만들지 않고 대화 안에서 문장만 다듬을 수도 있다. 파일 생성·변환은 실제 설치된 공식 스킬과 도구가 있을 때만 가능하다. 변환기가 없으면 PDF를 임의로 다시 만든 뒤 변환에 성공했다고 보고하지 않는다.

## PPT는 HTML 시안부터 확인한다

기존과 같은 `/dev-document-author`로 요청한다. 별도 디자인 스킬 이름이나 플러그인 이름을 외울 필요는 없다.

```text
/dev-document-author 현재 프로젝트의 사용자 안내 PPT를 새로 작성해줘.
```

신규·큰 디자인 변경이면 다음 순서로 진행한다.

```text
내용·목차 확인 → 실제 내용으로 대표 페이지 2~3개의 HTML A/B안 작성
→ 로컬 비교 링크 또는 열 수 있는 HTML 파일 제공 → 사용자 선택 대기
→ 선택한 시안과 수정 의견으로 편집 가능한 PPTX 작성 → 내용·최종 화면 검증
```

첫 시안 응답에서 전체 PPT를 먼저 완성하지 않는다. 예를 들어 다음처럼 선택한다.

```text
A안으로 진행해줘. 절차 설명은 A안으로, 포트 표는 B안으로 하고 제목은 조금 작게 해줘.
```

작업 진행 승인은 디자인 선택이 아니다. 이미 제공한 양식이 같은 범위에서 승인됐거나 문구만 고치는 경우에는 비교를 반복하지 않는다. `시안 없이 바로 PPT로 만들어줘`라는 명시적 요청도 존중한다. 일반 DOCX/XLSX/CSV/PDF 작업에 PPT 시안 단계를 일괄 강제하지 않는다.

### 미리보기의 의미

HTML은 **PPT 제작용 HTML 시안**이며 실제 PPT를 렌더링한 이미지가 아니다. 최종 슬라이드 비율, 실제 문구·이미지, 글꼴·여백·색상 기준을 맞춰 디자인을 선택한다. 작은 화면에서는 슬라이드 전체를 축소하거나 동일 비율로 스크롤해 보고 내용 배치를 바꾸지 않는다.

PPT 렌더러가 없어도 HTML 시안은 제시한다. 최종 PPT는 선택한 HTML을 기준으로 텍스트·표·도형을 재구성하며 전체 슬라이드를 이미지 한 장으로 붙이는 방식은 기본으로 쓰지 않는다. 최종 글꼴·줄바꿈·겹침은 별도로 검사하고, 검사하지 못했다면 미검증으로 보고한다.

### 로컬 검토 보드와 피드백

플러그인 설치·서버 실행 방법은 `docs/design-plugins.md`를 따른다. `mock-review`를 사용할 수 있으면 스킬이 실제 작성한 시안을 등록하고 실제 URL과 검토 ID·회차를 안내한다. 기존 DevKit 샘플을 사용자 시안으로 대신하지 않는다. 대상 문서의 프로젝트 컨텍스트를 사용하며 DevKit 저장소의 디자인 프로필을 잘못 적용하지 않는다.

보드에 의견을 저장한 다음 **같은 Hermes 세션에서** “이 검토 ID의 이번 회차 의견을 읽고 반영해줘”라고 요청한다. `--no-wake`이므로 Send만으로 작업이 자동 재개되지 않는다. 이전 회차나 선택 없는 승인 표시를 근거로 디자인을 임의 확정하지 않는다.

플러그인·서버를 사용할 수 없으면 이유를 알리고 로컬 HTML로 비교할 수 있게 한다. `/opt/data` 내부 경로만 던져 주거나 가짜 localhost 링크를 만들지 않는다. 실제 Windows bind 경로나 첨부 가능한 파일로 전달한다. 전달 자체가 불가능하면 시안 제공 미완료로 남기며 전체 PPT를 만들어 생략하지 않는다.

HTML·decisions JSON은 시안 검토용 중간 자료다. 새로운 자동 실행 서비스, 별도 승인 DB, 외부 업로드, 플러그인·렌더러 자동 설치는 추가하지 않는다.

## DevKit 연결

새 스킬은 `custom-skills/shared/dev-document-author/`에 있다. 기존 shared 경로를 사용하므로 별도 서비스나 새로운 마운트를 추가하지 않는다. 기본 자동 로드는 기존 `dev-session`만 유지한다. 새 정책과 포맷 참조는 문서 작업 때 필요한 것만 읽는다.

변경 전 승인은 기존 DevKit 절차를 따른다. 기능 문서는 `dev-feature-docs`, API 계약은 `dev-api-docs`의 책임을 유지한다. 공식 스킬·사용자 원본·컨테이너 설정을 자동으로 초기화하거나 바꾸지 않는다. 업데이트를 반영한 뒤 새 Hermes 세션에서 스킬 본문이 실제로 읽히는지 확인한다.

## 자동 검증

저장소 루트에서 실행한다.

```bash
python3 custom-skills/shared/dev-document-author/tests/test_document_policy.py
python3 custom-skills/shared/dev-document-author/tests/test_html_preview_policy.py
bash scripts/verify.sh
```

기존 회귀 실행기가 신규 테스트를 자동으로 찾는다. 정책과 참조 파일, 예문의 보호 값, 스킬 등록, 기본 자동 로드 유지 여부를 검사한다. 이 테스트는 실제 LLM 문장 생성이나 DOCX/PDF 렌더링 테스트가 아니다. 별도 외부 모델 호출이나 문서 생성 의존성을 CI에 추가하지 않는다.

## 실제 환경에서 확인할 항목

| 요청 | 확인할 결과 |
|---|---|
| 신규 PPT, 렌더러 없음 | 실제 내용의 HTML 시안 제시 후 대기; 선택 후 제작; 최종 PPT 화면은 미검증으로 분리 |
| 보드 미가동 | 이유와 로컬 HTML 경로 제공; 가짜 URL·임의 선택·자동 설치 없음 |
| 이전 회차·선택 없는 의견 | 현재 시안에 대한 선택 확인 전 전체 PPT 생성 없음 |
| 한국어 가이드 DOCX/PDF | 내용 일치, 한글 글꼴, 표 잘림, 변환 여부 |
| 기존 문서 부분 수정 | 범위 밖 내용과 자연스러운 기존 표현 보존 |
| PPTX 제목·노트 수정 | 수치·슬라이드 구성 유지, 텍스트 겹침 여부 |
| XLSX 제목·설명 수정 | 수식·셀 값·시트 보존, 필요한 계산 검증 |
| 공식 스킬·변환기 없음 | 해당 출력만 미완료, 임의 설치나 성공 보고 없음 |

가상 자료로 확인하고 실행 환경, 읽은 스킬, 명령·결과, 미검증 항목을 기록한다. 자동 테스트 통과만으로 위 항목을 통과했다고 표시하지 않는다. Windows updater의 모의 검증 역시 사용자 PC에서 실제 업데이트한 결과와 구분한다.
