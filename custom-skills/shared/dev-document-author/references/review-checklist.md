# 문서 검토 기준

현재 세션에서 작성자 관점의 자체 검토를 한다. 별도 Reviewer, 추가 승인, 점수 기반 차단을 만들지 않는다.

## 내용과 문체

- 원문·근거와 비교해 수치·단위·조건·부정·예외·의무 수준·출처가 보존됐는가?
- 독자가 쓰는 용어와 문체인가? 번역투·추상적인 칭찬·불필요한 명사 표현을 줄였는가?
- 이미 자연스러운 문장과 기술 용어를 억지로 바꾸지 않았는가?
- 내용을 구체화한다는 이유로 기능·주체·성과·감정·경험을 만들어 넣지 않았는가?
- 제목·표 헤더·캡션·노트가 본문과 같은 용어를 쓰는가? 도입과 결론이 불필요하게 반복되지 않는가?
- 대화용 인사, 자기평가, 스킬 실행 기록이 제출 문서에 들어가지 않았는가?

## 파일과 표시 상태

요청한 포맷만 검증한다. 원본과 범위 밖 변경은 보존하고 아래 검사를 분리해서 기록한다.

| 검증 | 확인 내용 |
|---|---|
| 내용 검증 | 결과를 다시 읽어 누락·추가·수치 변경·표/링크 손상을 원문과 비교 |
| 구조 검증 | 포맷별 공식 도구로 정상 읽기·페이지/슬라이드/시트·필수 요소 확인 |
| 시각 검증 | 필요한 페이지·슬라이드·표를 렌더링해 한글 글꼴, 줄바꿈, 표 잘림, 겹침 확인 |
| 계산 검증 | XLSX의 수식·참조·오류·계산 결과 확인. 단순 저장 성공으로 대체하지 않음 |
| 변환 검증 | 원본과 변환본의 내용·조건·레이아웃 비교. 재작성을 변환으로 보고하지 않음 |

각 항목은 `통과 / 실패 / 미실행 / 해당 없음`으로 구분하고 실행 근거를 남긴다. 도구나 글꼴 부족으로 실행하지 못했으면 그 이유를 보고한다. 종료 코드 0과 파일 존재만으로 성공을 단정하지 않는다. 자연스러움을 정적 테스트나 AI 탐지기로 인증하지 않는다.

## 예문 검토

`tests/fixtures/cases.json`은 모두 가상 예시다. `before`와 제안 문장 `after`를 비교하며 `protected`와 `review`를 확인한다. `reject`는 의미가 바뀌거나 과장이 남은 반례다. `after`와 정확히 같은 문장만 정답으로 강제하지 않는다. 다른 표현도 의미를 보존하고 자연스러우면 허용한다.

자동 테스트는 예문의 형식·보호 값·규칙 참조가 깨지지 않았는지만 검사한다. 실제 모델 출력의 품질은 예문에 대한 생성·수정 결과를 읽고 판단한다. 테스트 수나 단어 수를 문체 점수로 사용하지 않는다.

## 실제 사용 점검

신규 한국어 가이드(DOCX/PDF), 기존 문서 부분 수정, 안내문, PPTX 제목/노트, XLSX 표 헤더를 각각 요청해 본다. 한국어·표·수치·조건이 포함된 가상 자료를 사용한다. 실행한 환경의 Hermes 버전, 실제 읽은 스킬, 명령·결과, 미검증 항목을 기록한다. 스킬이 없거나 변환기가 없는 경우도 확인한다. 사용자 파일이나 운영 설정을 테스트용으로 바꾸지 않는다.
